One thing I'd verify before calling it done
You said the InitiateCheckout pixel on QuoteOptions reads formData from parent state, not from the URL. Confirm what happens when a Private Mode user lands on QuoteOptions via a page refresh.
Scenario: Private Mode user completes the form → lands on the quote page → refreshes the page (or returns from a tab switch on iOS, which on Safari Private Mode can effectively reload).
If QuoteOptions is rendered as part of /final-quote, and the parent's formData state is reconstructed from the URL on mount (since sessionStorage failed), then the parent rebuilds formData using only the fields you kept in the URL — prices, vehicle, locations. The InitiateCheckout pixel then fires with those fields, which you said is all it uses. Fine.
But if QuoteOptions is on a different route the user navigates to after /final-quote, and that route also reconstructs from sessionStorage → URL fallback chain → it depends entirely on whether that next page has its own URL-based fallback. If it doesn't, the user lands on a blank QuoteOptions and the pixel fires with undefined values (or doesn't fire at all).
Worth tracing for 60 seconds: on a Private Mode page refresh of QuoteOptions, does the InitiateCheckout pixel still get the price/vehicle/location it needs? If yes, fully clear to deploy. If no, you've got a small downstream version of the same bug.
